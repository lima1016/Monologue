# Monologue Phase 2 — 학습 흐름 재설계

## 개요

Phase 1은 기능이 도는 것을 목표로 했고, 그 결과 화면은 와이어프레임에 머물렀다.
CSS 3KB, 브라우저 기본값 위에 파란 버튼 하나. Phase 2는 **UI/UX를 다시 짜고,
학습에 실제로 기여하는 기능을 추가한다.**

Phase 1과의 관계: 백엔드 구조(FastAPI + SQLite + Ollama + Kokoro/VOICEVOX)와
`docs/superpowers/specs/2026-08-29-monologue-design.md`의 LLM 전략은 그대로
유지한다. 바뀌는 것은 프론트엔드 전체, 피드백 스키마, 그리고 화면 구성이다.

## 목표

- 말하기 한 턴이 **클릭 한 번**으로 끝난다 (지금은 두 번)
- 교정을 *읽고 넘기는* 대신 **고쳐서 다시 말하게** 한다
- 홈 / 세션 / 마이페이지 3화면으로 나누고, 밝고 깔끔한 디자인 시스템을 세운다
- 이미 저장하고 있으나 쓰지 않는 데이터(내 녹음)를 화면에 연결한다
- 교정 피드백이 **한국어로 안정적으로** 나오게 한다 (현재 깨져 있음)
- 학습 이력에서 **약점과 복습 문장**을 뽑아 보여준다

## 비목표

- 단어장, 문법 설명 페이지, 객관식 퀴즈 — 하지 않는다. 말하기 앱에 넣으면
  결국 말하지 않게 된다.
- 멀티유저, 배포, 인증 — Phase 1의 비목표를 그대로 유지한다.
- DB 엔진 교체 — 아래 "SQLite를 유지하는 이유" 참고.
- 모델 상향 — 아래 "스파이크 결과" 참고.

## 스파이크 결과 (2026-08-29, 확정)

설계 전에 `qwen2.5:14b`로 검증을 돌렸다. 검증 스크립트는 스크래치패드에 둔
버리는 코드이며 저장소에 포함하지 않는다.

### 문제

`messages.correction`에 **영어가 저장되어 있다**. 예: `"The sentence is
grammatically correct."` 프롬프트는 한국어를 요구하는데 모델이 따르지 않는다.
직전 커밋 `6d705d8 fix: try Korean-tutor identity anchor for feedback prompt
(partial)`의 그 "(partial)"이 이 상태다.

### 측정 결과

| 항목 | 현재 프롬프트 | 처방 적용 후 |
|---|---|---|
| 교정이 한국어로 | 불안정 | 영어 10/10 · 일본어 8/8 |
| `ok` (맞음/틀림) 판정 | — | 영어 10/10 · 일본어 8/8 |
| `tag` 정확도 | — | 영어 8/10 · 일본어 8/8 |
| 응답 속도 | 3.1초/문장 | 3.1초/문장 (변화 없음) |

### 확정된 처방 세 가지

1. **시스템 프롬프트를 한국어로 쓴다.** 현재 `build_feedback_messages`는 *영어로*
   "한국어로 써라"라고 지시한다. 지시문 자체가 영어면 출력이 영어로 끌린다.
   프롬프트를 한국어로 옮기는 것만으로 언어 문제가 해소됐다.

2. **태그 목록을 언어별로 나눈다.** 일본어에 `전치사` 칸을 주면 조사 오류가 갈
   곳이 없어 `어순`으로 밀린다. 언어별로 나눈 뒤 6/8 → 8/8.

   ```
   en: 시제 / 관사 / 전치사 / 어순 / 어휘 / 단복수 / 없음
   ja: 시제 / 조사 / 활용 / 어순 / 어휘 / 경어  / 없음
   ```

3. **태그마다 한 줄 정의를 붙이고, 일관성을 명시한다.** 이름만 나열하면 모델이
   감으로 찍는다. `조사 - は, が, に, で, を, の 같은 조사를 잘못 골랐음`처럼
   한 줄씩 주고, "tag는 correction에서 실제로 지적한 내용과 일치해야 한다"를
   덧붙인다.

### 모델을 바꾸지 않는 이유

- 원인이 프롬프트였고 프롬프트로 해결됐다.
- VRAM 16GB(RTX 4060 Ti)에서 32b급은 Q4로도 ~19GB라 들어가지 않는다. CPU로
  넘치면 턴당 수십 초가 되어 말하기 연습에 못 쓴다. 시스템 RAM 64GB는 도움이
  되지 않는다 — 병목은 VRAM이다.
- 이 앱은 **매 턴 LLM을 두 번** 부른다(`_feedback()` + `llm.chat()`). 모델을
  키우면 교정 품질 하나 때문에 앱 전체가 느려진다.

### 남은 한계 — 설계에 반영함

태그 정확도는 90% 언저리이지 100%가 아니다. 영어 오답 하나는 진짜 미스였고
(`He don't like coffee.` → `단복수`가 아니라 `시제`로 찍음, 설명은 정확했음),
하나는 사람이 봐도 애매한 문장이었다(`I very like this restaurant.` — 어순인지
어휘인지).

따라서:

- **마이페이지 「자주 걸리는 것」 막대그래프에는 태그를 쓴다.** 수십 번 누적된
  카운트에서 10% 오분류는 순위를 뒤집지 않는다.
- **복습 목록은 태그가 아니라 문장 자체로 뽑는다.** `correction`과 `fixed`는
  항상 정확했으므로, "내가 틀린 문장"을 직접 큐에 넣는다. 태그로 복습을 고르면
  가끔 엉뚱한 문장이 나온다.

## SQLite를 유지하는 이유

현재 `monologue.db`는 76KB, `sessions` 31행, `messages` 77행이다. 세션을 3만 개
쌓아도 SQLite에는 부담이 아니다. 그리고 이 앱에서 느린 것은 DB가 아니라 로컬
14b 모델이다 — 턴당 3초는 `llm.chat()`이고 DB 쿼리는 1ms 미만이다. Postgres로
바꾸면 Docker 서비스, 커넥션 풀, 마이그레이션 도구가 붙지만 체감 속도는 그대로다.
"전부 로컬, 운영비 0"이라는 전제와도 맞지 않는다.

### 그러나 마이그레이션 경로가 없다 — 반드시 먼저 고친다

`db.init_db()`는 `conn.executescript(SCHEMA)`만 실행하고, SCHEMA는 전부
`CREATE TABLE IF NOT EXISTS`다. `messages` 테이블이 이미 존재하므로 이 구문은
**통째로 건너뛴다.** 즉 SCHEMA에 컬럼을 추가해도 기존 `monologue.db`에는 영영
생기지 않고, 새 DB로 시작한 경우에만 동작하다가 `INSERT`에서 터진다.
저장소 전체에 `ALTER TABLE`도 `PRAGMA user_version`도 없다.

**해결**: `PRAGMA user_version`으로 스키마 버전을 관리하고, `init_db()`가 부족한
버전만큼 마이그레이션 단계를 순서대로 적용한다. SQLite의 `ADD COLUMN`은 즉시
끝나므로 구현은 짧다.

각 단계는 SQL 문의 리스트이고, `init_db()`는 현재 `user_version`부터 끝까지의
단계만 순서대로 실행한 뒤 버전을 갱신한다. 단계는 **추가만 하고 기존 것을 고치지
않는다** — 이미 적용된 단계를 수정하면 DB마다 스키마가 갈린다.

```python
MIGRATIONS = [
    # index 0: v0 -> v1  (Phase 1 스키마 = 현재 SCHEMA 상수)
    # index 1: v1 -> v2  [A단계]
    ["ALTER TABLE messages ADD COLUMN ok INTEGER",
     "ALTER TABLE messages ADD COLUMN fixed TEXT",
     "ALTER TABLE messages ADD COLUMN tag TEXT"],
    # index 2: v2 -> v3  [C단계] user_scenarios (아래 "데이터 모델 변경"의 DDL)
    # index 3: v3 -> v4  [D단계] review_queue   (아래 "데이터 모델 변경"의 DDL)
    # index 4: v4 -> v5  [E단계] sessions.shadowing
]
```

기존 DB는 `user_version`이 0이므로, 첫 실행 시 v0 단계를 건너뛰도록 Phase 1
스키마가 이미 적용된 DB를 v1로 표시하는 처리가 필요하다 — `sessions` 테이블이
존재하면 `user_version = 1`로 찍고 시작한다.

기존 31개 세션은 전부 1~2턴짜리 스모크 테스트 데이터이므로 백필하지 않는다.
새 컬럼은 NULL로 남고, 통계는 NULL을 제외하고 집계한다.

## 단계

각 단계가 끝나는 시점에 **실제로 쓸 수 있는 앱**이 되도록 자른다. 중간에 멈춰도
손해가 없어야 한다.

**단계마다 별도의 구현 계획을 쓴다.** 이 문서는 A~E 전체의 설계이고, 구현 계획은
한 단계씩 만든다 — 다섯 단계를 한 계획에 담으면 계획 자체가 따라가기 어려워지고,
앞 단계에서 배운 것을 뒤 단계에 반영할 여지가 없어진다.

### A · 토대

- `PRAGMA user_version` 마이그레이션 프레임워크
- `FEEDBACK_SCHEMA`에 `ok` / `fixed` / `tag` 추가 + **스파이크에서 확정된 프롬프트
  처방 3가지 적용** (한국어 시스템 프롬프트, 언어별 태그, 태그 정의)
- `messages`에 `ok` / `fixed` / `tag` 컬럼
- `app.js` 모듈 분리 + 디자인 시스템 CSS + 화면 라우팅

**A를 먼저 하는 이유**: D의 그래프와 복습은 태그가 쌓인 만큼만 나온다. A를
나중으로 미루면 B·C를 만드는 동안 연습한 기록이 전부 태그 없이 남아 **D를
만들어도 화면이 빈다.** A를 먼저 해두면 이후 작업 기간 내내 데이터가 쌓인다.

*완료 시점의 상태: 화면은 아직 Phase 1 그대로. 그러나 교정이 한국어로 나오고
태그가 쌓이기 시작한다.*

### B · 세션 화면

- 대화 + 우측 패널 레이아웃, 밝고 깔끔한 스타일
- 자동 전송 + 되돌리기
- 접히는 교정 칩 + 펼치기
- **재발화** (`🎤 고쳐서 다시 말해보기`)
- 생각 중 표시, 녹음 중 표시
- **내 녹음 재생** — 재생용 GET 엔드포인트 신설 필요

*완료 시점의 상태: 앱이 완전히 달라진다. 단독으로 충분히 쓸 만하다.*

### C · 홈

- 통합 입력창 + 칩 (시나리오 select 제거)
- **LLM 시나리오 생성** + `user_scenarios` 테이블
- 이어서 하기 + 유령 세션 정리
- **i+1** 프롬프트

### D · 마이페이지

- 누적 레벨 판정 + 표본 부족 시 정직한 표시
- 태그 집계 막대그래프
- **복습 목록** (문장 단위, 간격 반복)
- 세션 기록 + 리포트 열람

### E · 새 모드

- **쉐도잉**
- **1분 말하기**

## 데이터 모델 변경

### `messages` — 컬럼 추가

| 컬럼 | 타입 | 용도 |
|---|---|---|
| `ok` | INTEGER | 문법적으로 맞았는지 (0/1). 교정 칩이 `✓ 문장 정확`을 띄울 근거 |
| `fixed` | TEXT | 고친 문장만. 재발화와 복습이 읽는 값 |
| `tag` | TEXT | 오류 범주. 언어별 목록 중 하나 |

기존 `correction` / `suggestion`은 산문 설명으로 그대로 유지한다 (칩을 펼쳤을 때
보여주는 내용).

### `user_scenarios` — 신설

LLM이 생성한 시나리오를 담는다. `data/scenarios.json`은 기본 제공분으로 남기고
읽기 전용으로 둔다 — 현재 `scenarios.py`의 카탈로그는 `@lru_cache`가 걸린 JSON
파일이라, 여기에 쓰기를 섞으면 캐시 무효화와 파일 쓰기 경쟁을 직접 다뤄야 한다.

```sql
CREATE TABLE user_scenarios (
    id            TEXT PRIMARY KEY,   -- "user-면접-1735..." 형태
    language      TEXT NOT NULL,
    type          TEXT NOT NULL,      -- free | script
    title         TEXT NOT NULL,
    goal          TEXT,
    persona_prompt TEXT,              -- free
    max_turns     INTEGER,            -- free
    lines_json    TEXT,               -- script
    created_at    TEXT NOT NULL,
    used_count    INTEGER NOT NULL DEFAULT 0
);
```

`scenarios_for(language, mode)`가 JSON 카탈로그와 이 테이블을 합쳐 반환한다.
생성된 시나리오는 저장 전에 기존 `scenarios._validate()`를 그대로 통과시킨다.

### `review_queue` — 신설

복습은 태그가 아니라 문장 단위다.

```sql
CREATE TABLE review_queue (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    message_id  INTEGER NOT NULL REFERENCES messages(id),
    language    TEXT    NOT NULL,
    due_at      TEXT    NOT NULL,
    interval_d  INTEGER NOT NULL DEFAULT 1,
    passed      INTEGER NOT NULL DEFAULT 0,
    UNIQUE(message_id)
);
```

`ok = 0`인 발화가 생기면 `due_at = 내일`로 큐에 넣는다. 복습에서 다시 말해
성공하면 `interval_d`를 1 → 3 → 7 → 14로 늘리고, 실패하면 1로 되돌린다.
`passed`가 3에 도달하면 큐에서 내린다.

### "다시 말해 성공"의 판정 기준

재발화와 복습 모두 같은 판정을 쓴다. **STT 결과를 `fixed`와 정확히 일치시키는
것을 요구해서는 안 된다** — 브라우저 음성인식은 문장부호를 돌려주지 않고
대소문자도 제멋대로라, 정확 일치를 요구하면 사용자가 제대로 말해도 영원히
통과하지 못한다.

```
정규화: 소문자화 → 문장부호 제거 → 연속 공백 축약 → 앞뒤 공백 제거
비교:   en  단어 단위 유사도 (토큰 시퀀스)
        ja  문자 단위 유사도 (공백으로 나뉘지 않으므로)
통과:   유사도 0.9 이상
```

이 판정 함수는 순수 함수로 분리해 테스트한다 (아래 "테스트" 참고).

## API 변경

### 신설

| 메서드 | 경로 | 용도 |
|---|---|---|
| `GET` | `/api/messages/{id}/audio` | **내 녹음 재생.** 현재 업로드(`POST`)만 있고 되받을 방법이 없다 |
| `DELETE` | `/api/sessions/{id}/last-turn` | 되돌리기. 마지막 user+bot 메시지를 지운다 |
| `POST` | `/api/scenarios/generate` | 한 줄 설명 → LLM이 시나리오 생성 → `user_scenarios`에 저장 |
| `GET` | `/api/stats` | 마이페이지: 누적 레벨, 태그 집계, 세션/발화 수, 연속일 |
| `GET` | `/api/review` | 오늘 복습할 문장 목록 |
| `POST` | `/api/review/{id}/result` | 복습 결과 기록 (간격 갱신) |
| `GET` | `/api/sessions/open` | 이어서 할 수 있는 중단 세션 |

### 변경

- `POST /api/chat` 응답에 `ok` / `fixed` / `tag` 추가
- `GET /api/scenarios` 응답에 사용자 생성분 포함

### 되돌리기의 의미

되돌리기는 마지막 턴을 **버린다**. 잘못 인식된 문장에 달린 봇 응답과 교정은
학습 기록으로서 가치가 없으므로 남기지 않는다. 삭제 후 사용자가 고친 문장으로
다시 `POST /api/chat`을 호출하면 정상 흐름으로 이어진다.
`messages`의 `UNIQUE(session_id, turn)` 제약은 마지막 두 행을 지우고 다시
INSERT하는 방식과 충돌하지 않는다.

## 프론트엔드 구조

### 왜 분리하는가

현재 `static/app.js`는 13KB 단일 파일이다. Phase 2에서 추가되는 것(라우팅, 3개
화면, 상태 머신, 쉐도잉, 1분 말하기, 복습)을 그대로 얹으면 4배가 되어 사람도
모델도 안정적으로 고치지 못하는 파일이 된다.

```
static/
  index.html
  css/
    tokens.css      색·타이포·간격 스케일
    base.css        리셋, 타이포그래피
    components.css  버튼, 말풍선, 칩, 카드, 패널
  js/
    api.js          fetch 래퍼 (기존 $ / api / getJSON / postJSON)
    router.js       홈 / 세션 / 마이페이지 전환
    audio.js        TTS 재생, 녹음, STT (기존 play / speakInBrowser / recorder)
    session.js      대화 상태 머신, 턴 처리
    feedback.js     교정 칩 렌더링, 펼치기, 재발화
    home.js         통합 입력창, 시나리오 생성, 이어서 하기
    mypage.js       레벨, 그래프, 복습, 이력
    shadowing.js    쉐도잉 모드
    timed.js        1분 말하기 모드
```

빌드 도구는 도입하지 않는다. ES 모듈(`<script type="module">`)로 충분하다.

### 상태 머신 — `state.busy` 플래그로는 부족하다

현재 재진입 방지는 불리언 하나다(`07caa64`가 정확히 그 버그를 고친 커밋이다).
Phase 2에서는 상태가 늘어난다:

```
idle → listening → transcribing → sending → speaking → idle
                                     ↓
                                  undoing
                                     ↓
                              respeaking (재발화)
```

각 상태에서 어떤 버튼이 활성인지를 상태 머신 한 곳에서 결정한다. 마이크·보내기·
되돌리기·다음이 각자 `disabled`를 토글하는 현재 방식은 조합이 늘면 반드시 어긋난다.

## 화면

### 홈

```
오늘은 뭘 연습할까요?
┌──────────────────────────────┐
│ 구직 면접                     │  ← 자유 입력. 카탈로그에 없으면 LLM이 생성
└──────────────────────────────┘
  레스토랑  공항 체크인  스탠드업 회의     ← 기존 시나리오는 칩으로
  비워두면 봇이 골라줍니다

  자유 ●   스크립트 ○   수업 ○
```

- **시나리오 select를 제거한다.** "2개 중 고르세요"와 "뭐든 만들어 드립니다"가
  한 화면에 공존할 수 없다. 수업 모드의 `topic` 입력이 이미 이 모양이며, 그것을
  세 모드 전체로 넓히는 것이다.
- 모드 3개는 유지한다. 자유·스크립트·수업은 실제로 다른 경험이다.
- **이어서 하기**: `ended_at IS NULL`인 세션이 현재 8개 떠 있다. 가장 최근 1개만
  제안하고, 24시간이 지난 나머지는 종료 처리한다.
- **오늘의 추천**: 태그 집계 기반. 표본이 부족하면 이 카드를 숨긴다.
- 하단 통계(연속 학습일, 이번 주 발화, 고친 표현)는 기존 테이블로 계산된다.

### 세션

- 좌측 대화, 우측 패널(목표 + 교정 누적). 스크립트 모드에서는 우측이 대본 패널이
  된다. 세 모드가 같은 골격을 공유한다.
- 하단에 마이크 하나. 누르고 말하면 자동 전송된다.
- 봇 응답 대기 중 `● ● ●`. 현재는 몇 초 동안 화면이 완전히 정지한다.
- 교정은 말풍선 바로 아래 한 줄로 접힌다: `고칠 곳 1` 또는 `✓ 문장 정확`.
  누르면 그 자리에서 `correction`과 `suggestion` 전문이 펼쳐진다.
- 펼친 상태에 **`🎤 고쳐서 다시 말해보기`** 버튼. `fixed`를 읽고 다시 말한 뒤
  일치하는지 확인한다. 교정을 읽고 넘기면 다음 턴에 똑같이 틀린다.
- 내 발화 말풍선에 재생 버튼. 봇의 원어민 발음과 나란히 들을 수 있다.

### 마이페이지

- **레벨**: **최근 5세션**의 판정을 모아 최빈값으로 정한다. 현재는 유저 발화
  1턴짜리 세션 하나로 레벨을 매겨 `beginner ↔ intermediate`가 매번 튄다
  (#20 beginner → #21 intermediate → #24 intermediate → #28 beginner, 전부 같은
  시나리오). **표본 기준: 해당 언어로 종료된 세션이 3회 미만이거나 누적 유저
  발화가 15회 미만이면 레벨을 표시하지 않고 "판정하기엔 아직 이릅니다"로 둔다.**
  숫자를 꾸며내지 않는다.
- **자주 걸리는 것 / 잘하는 것**: 태그 집계 막대그래프.
- **복습**: 문장 단위 큐. 그래프보다 위에 둔다 — "전치사 5회"를 아는 것으로는
  실력이 늘지 않고, 그 5개 문장을 다시 말해야 는다.
- **지난 수업**: 세션 목록 + 리포트. `sessions`/`messages`로 바로 나오며
  `GET /api/sessions`도 이미 있다.
- **빈 상태가 기본이다.** 기존 31개 세션이 전부 테스트 데이터이므로 실제로는
  여기서 시작한다. 세션 3회 미만이면 빈 상태 화면을 보여준다.

## 새 모드

### 쉐도잉 — 새 모드가 아니라 스크립트 모드의 변형

**`mode`를 늘리지 않는다.** 쉐도잉은 대본이 필요하고 대본 진행 로직이 스크립트
모드와 같으므로, `sessions`에 `shadowing INTEGER DEFAULT 0` 플래그를 두고
`mode = 'script'`를 그대로 쓴다. 홈에서는 스크립트를 고르면 그 아래 토글로
나타난다. 카탈로그·대본 렌더링·진행 상태를 전부 재사용할 수 있다.

현재 스크립트 모드는 대본을 **글자로 다 띄워놓고 읽게** 한다. 그것은 낭독이지
쉐도잉이 아니다. 발음·억양·리듬이 느는 것은 소리를 먼저 듣고 즉시 따라할 때다.

필요한 부품은 전부 이미 있다 — TTS, 브라우저 STT, `MediaRecorder`. 텍스트를
가리고 오디오를 먼저 재생한 뒤 따라 말하게 하고, 그다음 텍스트를 공개해 비교한다.

```
1. 봇 대사 오디오 재생 (텍스트 숨김)
2. 사용자가 따라 말함 (녹음 + STT)
3. 텍스트 공개 + 내 발화와 나란히 비교 + 두 녹음 재생
4. 다음 줄
```

### 1분 말하기 — 이쪽은 진짜 새 모드

한 주제로 60초 동안 끊지 않고 말한다. **교정은 중간에 끼어들지 않고 끝난 뒤
한꺼번에** 보여준다. 매 턴 교정이 들어오면 정확도는 올라가도 유창성은 늘지 않는다.

- `mode`에 `timed`를 추가한다. 이는 `api.py`의
  `Mode = Literal["free", "script", "lesson"]`과 `prompts.build_system_prompt`의
  모드 분기를 함께 고쳐야 한다는 뜻이다.
- 진행 중에는 `_feedback()`을 호출하지 않고 발화만 누적한다.
- 종료 시 누적 발화 전체에 대해 교정을 일괄 요청한다. 발화 수만큼 LLM을 부르지
  않도록, 한 번의 호출로 여러 문장을 처리하는 프롬프트를 따로 만든다.

## 테스트

- 백엔드: 기존 `pytest -m "not engine"` 체계를 유지하고, 마이그레이션·되돌리기·
  복습 간격 계산·태그 집계에 테스트를 추가한다. 마이그레이션은 **구 스키마 DB를
  픽스처로 만들어** 실제로 컬럼이 추가되는지 확인한다 — 이 버그의 성격상
  새 DB로만 테스트하면 잡히지 않는다.
- 프론트엔드: 현재 테스트가 0개다. 상태 머신 전이만이라도 순수 함수로 분리해
  테스트한다. DOM 렌더링까지 자동화하지는 않는다.
- 피드백 품질: 스파이크에 쓴 채점 세트를 `tests/`에 `-m engine` 마커로 옮겨,
  프롬프트를 고칠 때 회귀를 잡을 수 있게 한다.
