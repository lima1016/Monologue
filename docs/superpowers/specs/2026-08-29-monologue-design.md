# Monologue — 개인용 음성 상황극 스피킹 연습 앱 설계

## 개요
영어/일본어 스피킹을 혼자 연습하기 위한 개인용 웹앱. 로컬 LLM 봇과 음성으로
상황극 대화를 하고, 문법/표현 교정 피드백과 세션 리포트를 받는다. 운영 비용은
$0을 목표로 한다 (로컬 LLM + 브라우저 내장 음성 API만 사용).

## 목표
- 실제 여행/일상/회사에서 벌어질 수 있는 상황을 음성으로 롤플레이하며 말하기 연습
- 자주 쓰이는 회화 스크립트를 대본처럼 보면서 봇과 함께 배우처럼 연기하는 연습
- 봇 선생님과 대화하며 문법 등을 배우는 정규 수업 느낌의 모드, 내 수준에 맞게 진행
- 대화 중/후 문법 교정 + 더 나은 표현 추천 (각 최대 2문장)
- 대화 스크립트, 교정 기록이 전부 로그로 남음
- 세션(상황극/수업 1회) 종료 시 수업 리포트 생성, 리포트로 실력 수준을 자동 추정
- 완전 개인용, 배포/멀티유저 고려 없음

## 비목표
- 회원가입/인증, 멀티유저, 배포 — 하지 않음
- 자체 LLM 파인튜닝 — 하지 않음. 이유는 아래 "LLM 전략" 참고.

## LLM 전략 — 파인튜닝 대신 프롬프트
기존 오픈소스 모델(Qwen)을 그대로 쓰고 파인튜닝하지 않는다.

- 파인튜닝은 모델의 *능력*이 아니라 *스타일/형식*을 바꾼다. Qwen은 이미 대규모
  다국어 데이터로 학습되어 있어, 소규모 추가 학습으로 영/일 문법 실력이 오르지
  않는다. 오히려 catastrophic forgetting으로 전반적 대화 품질이 나빠질 위험이 있다.
- 학습 데이터를 더 큰 모델로 생성하면 성능 상한이 그 모델이 된다 (증류). 위로
  올라가는 게 아니라 아래로 내려가는 선택.
- 품질 개선 ROI 순서: ①프롬프트 엔지니어링 ②few-shot 예시 ③더 큰 베이스 모델
  ④구조화 출력 강제 ⑤파인튜닝. ①~④를 다 하기 전에 ⑤로 가지 않는다.

재검토 조건: 실제 사용 기록(`messages` 테이블에 쌓이는 대화·교정·추천)이 충분히
축적되고, 원하는 출력 형식이 명확해졌을 때. 그때 LoRA로 형식을 고정해 더 작고
빠른 모델로 갈아타는 것은 실질적 이득이 될 수 있다. 즉 이 앱 자체가 향후
파인튜닝용 데이터셋 수집 장치 역할을 한다.

### 구어체 강제 — TTS 품질만큼 중요한 문제
"봇이 자연스러운가"는 음성 합성 품질과 **봇이 쓰는 말 자체**의 두 축으로 나뉜다.
LLM은 기본적으로 문어체로 쓴다 — 긴 문장, 격식 있는 연결어, 축약형 없음. 아무리
좋은 TTS를 써도 원어민이 실제로 쓰지 않는 문장을 읽어주면 회화 학습에 해롭다.

시스템 프롬프트에 다음을 명시적으로 강제한다.
- 축약형 사용 (I'm, don't, gonna 등), 짧은 문장, 구어 표현
- 한 번에 1~3문장 이내 (음성으로 듣기 때문에 긴 응답은 부담)
- 마크다운·이모지·목록·괄호 설명 금지

또한 LLM 출력을 TTS에 넘기기 전에 **정제 단계**를 둔다. 마크다운 기호, 이모지,
그 외 소리 내어 읽으면 어색한 문자를 제거하고 길이 상한을 적용한다. 이 정제는
TTS 입력에만 적용하고, 화면 표시와 DB 저장에는 원문을 쓴다.

Qwen의 영어 구어체는 자연스러운 편이나 일본어는 다소 딱딱할 수 있다. 구현 초기에
두 언어 모두 실제 출력을 확인하고, 필요하면 few-shot 예시를 프롬프트에 넣는다.

## 아키텍처
- **Backend**: FastAPI (Python) 단일 서버, 로컬 실행 전용
- **LLM**: Ollama + Qwen2.5(또는 3) 14B급, `http://localhost:11434` REST 호출
- **TTS**: 로컬 신경망 TTS를 서버에서 생성 (아래 "봇 음성" 참고)
- **Frontend**: 단일 HTML + 바닐라 JS 페이지
  - STT: 브라우저 내장 `SpeechRecognition` (Web Speech API)
  - 봇 음성 재생: 서버가 생성한 오디오를 `<audio>`로 재생
  - 인식된 텍스트를 수정할 수 있는 입력창을 STT 옆에 병행 제공 (일본어 인식률 보완)
  - 오디오 녹음: `MediaRecorder`로 발화 오디오를 STT와 **병행 수집** (아래 참고)
- **저장소**: SQLite 파일 하나 (`monologue.db`) + 오디오 파일은 `audio/` 디렉터리

### 오디오 캡처 경로 (Phase 1에서 미리 준비)
Web Speech API는 인식 텍스트만 주고 원본 오디오를 주지 않는다. 발음 평가(Phase 2)에
오디오가 필요하므로, Phase 1부터 `MediaRecorder`로 발화를 병행 녹음해
`POST /sessions/{id}/audio`로 업로드하고 `messages.audio_path`에 경로를 남긴다.
Phase 1에서는 저장만 하고 분석하지 않는다. 이렇게 하면 Phase 2에서 프론트엔드
구조를 다시 갈아엎지 않아도 되고, Phase 1 사용 기록도 나중에 소급 분석할 수 있다.

동작 환경은 Chrome 기준으로 가정한다 (Web Speech API 지원이 가장 안정적).

## 봇 음성 (TTS)

### 왜 브라우저 TTS를 쓰지 않는가
이 PC에 설치된 OS 음성을 조사한 결과, 영어는 구형 SAPI 음성(David/Mark/Zira)뿐이고
**일본어 음성은 아예 설치되어 있지 않다**. 발음을 따라 배우는 앱에서 로봇 같은
음성은 학습 대상으로 부적절하고, 일본어는 재생 자체가 불가능하다. 브라우저 자체
음성(Chrome의 Google 음성 등)은 이보다 낫지만 네트워크 의존적이고 품질 상한이 낮다.
따라서 로컬 신경망 TTS를 서버에서 돌린다.

### 교체 가능한 TTS 인터페이스
TTS는 `synthesize(text, language, voice) -> audio bytes` 형태의 얇은 인터페이스
뒤에 둔다. 백엔드 구현체를 바꿔도 나머지 코드가 영향받지 않게 한다.
**언어별로 다른 백엔드를 쓴다.**

### 엔진 선정 (실제 샘플 청취 후 결정)
후보들을 실제로 설치해 같은 문장으로 샘플을 생성하고 직접 들어본 뒤 결정했다.

| 언어 | 엔진 | 근거 |
|---|---|---|
| 영어 | **Kokoro** (`kokoro-onnx`) | 브라우저 음성보다 확연히 자연스러움 |
| 일본어 | **VOICEVOX** (로컬 HTTP 엔진) | Kokoro보다 억양이 뚜렷하게 자연스러움 |

측정 과정에서 확인된 사실들:

- **Kokoro의 일본어는 한자를 못 읽는다.** `kokoro-onnx`는 G2P에 espeak을 쓰는데
  한자에서 실패해, 같은 문장이 영어 4초 / 일본어 한자 19~24초로 3~4배 늘어지며
  깨진다. `pyopenjtalk`로 한자→가나 변환을 선행하면 4.7~6.2초로 정상화된다.
  즉 Kokoro로 일본어를 쓰려면 별도 G2P 단계가 필수다.
- VOICEVOX는 한자 처리와 피치 액센트가 엔진에 내장되어 이 문제가 없고, 청취
  비교에서도 더 자연스러웠다. 그래서 일본어는 VOICEVOX로 간다.
- VOICEVOX 음성은 캐릭터 지향이라 화자에 따라 연출이 강하다. 상황극 몰입을 위해
  비교적 중립적인 화자를 기본값으로 두고, 사용자가 바꿀 수 있게 한다.

### 음성 선택
두 언어 모두 **사용자가 음성을 고를 수 있게 한다.** 설정 화면에서 언어별 음성을
지정하고 선택은 `settings` 테이블에 영구 저장한다. 설정 화면에는 **미리듣기
버튼**을 두어 고정된 예시 문장을 그 음성으로 즉시 재생한다.

**영어 — 미국 발음만 노출한다.** Kokoro에는 영국 발음(`bf_`/`bm_`)도 있으나
학습 대상 발음이 섞이면 방해가 되므로 목록에서 제외한다. 미국 발음 20종을 모두
청취한 뒤 아래 5종으로 좁혔다.

| 음성 | 성별 |
|---|---|
| `am_adam` | 남성 — **기본값** |
| `am_fenrir` | 남성 |
| `af_heart` | 여성 |
| `af_bella` | 여성 |
| `af_kore` | 여성 |

**일본어** — VOICEVOX 화자 43종을 모두 청취한 뒤 아래 4종으로 좁혔다.
화자마다 캐릭터 연출 강도 차이가 커서, 상황극 몰입을 해치지 않는 쪽을 골랐다.

| 화자 | 스타일 | speaker id |
|---|---|---|
| 剣崎雌雄 | ノーマル | `21` — **기본값** |
| 青山龍星 | ノーマル | `13` |
| 琴詠ニア | ノーマル | `74` |
| 春日部つむぎ | ノーマル | `8` |

VOICEVOX는 화자별로 감정 스타일(熱血/囁き 등)을 추가로 제공하지만, 상황극에는
기본 스타일만 쓴다. 감정 스타일 활용은 향후 확장으로 남긴다.

### 운영 형태
- Kokoro는 앱 프로세스 안에서 직접 추론한다 (별도 서버 불필요, HTTP 홉도 없음).
  모델 파일만 `engines/kokoro/`에 둔다 (약 337MB, git 제외).
- VOICEVOX는 **Docker로 띄운다** (`docker-compose.yml`, `127.0.0.1:50021`).
  아래 "실행 구성" 참고.
- 앱 시작 시 VOICEVOX 헬스 체크를 하고, 죽어 있으면 화면에 안내한다.
- VOICEVOX는 무료로 쓸 수 있으나 사용 화자에 대한 크레딧 표기 의무가 있다.
  개인용이라 노출 대상은 없지만, README에 사용 사실과 화자명을 남겨둔다.
- **비상 폴백**: TTS 생성이 실패하면 브라우저 `speechSynthesis`로 자동 대체하고
  화면에 품질 저하를 알린다. 연습이 아예 중단되지는 않게 한다.

## 실행 구성 — 무엇을 Docker로 띄우고 무엇을 설치하는가
"가능하면 시스템에 직접 설치하지 않는다"를 기본 원칙으로 하되, 컴포넌트별로 판단한다.

| 구성요소 | 형태 | 근거 |
|---|---|---|
| **VOICEVOX** | **Docker** | 공식 이미지 존재. 설치 절차가 "1.7GB 아카이브 내려받아 압축 해제"에서 `docker compose up -d` 한 줄로 축소된다. `restart: unless-stopped`로 재부팅 후 자동 복귀 |
| **Ollama** | **네이티브 설치** | Windows에서 GPU를 쓰려면 Docker 경로는 WSL2 + NVIDIA Container Toolkit 계층이 추가된다. 추론이 성능 핵심 경로이므로 계층을 얇게 유지한다 |
| **Kokoro** | 앱 내부 | 서버가 아니라 파이썬 라이브러리. 컨테이너화 대상이 아니다 |
| **앱(FastAPI)** | 개발 중 네이티브 | 개발 루프에서 리빌드·볼륨 마운트 마찰이 생긴다. 안정화 후 컨테이너화는 선택사항 |
| **SQLite** | 해당 없음 | 파일 하나 |

Docker에 restart 정책을 걸면 서비스가 늘어도 실행 마찰은 오히려 줄어든다
(부팅 시 자동 기동). 다만 이는 *무엇을 띄울지*의 문제이지 *무엇이 적합한지*와는
별개다 — Elasticsearch는 Docker로 쉽게 띄울 수 있어도 여전히 규모가 맞지 않는다.

검증 완료: Docker 이미지 `voicevox/voicevox_engine:cpu-latest`로 기동해 네이티브와
동일하게 동작함을 확인했다 (버전 0.25.2, 화자 43종, 기본 화자 id=21 합성 정상).

### 지연 시간 관리
서버 생성은 브라우저 TTS와 달리 지연이 생긴다 (~0.3~1초 예상). 완화책:
- **오디오 캐싱**: 생성한 오디오를 텍스트+음성 해시로 캐싱한다. 스크립트 모드는
  대사가 고정이라 두 번째 세션부터 즉시 재생된다.
- **선생성(pre-generation)**: 스크립트 모드는 세션 시작 시 봇 대사를 미리 전부
  생성해둔다.
- 자유 상황극/수업 모드는 LLM 응답이 나온 직후 곧바로 TTS를 태워 체감 지연을 줄인다.

## 데이터 모델

세 가지 모드가 있다: `free`(자유 상황극), `script`(스크립트 롤플레이),
`lesson`(수업). 앞의 둘은 `scenarios.json`에 미리 정의된 콘텐츠를 쓰고,
`lesson`은 매번 그 자리에서 동적으로 구성된다 (고정 커리큘럼 없음).

### 시나리오 정의 (`scenarios.json`, 정적 파일)
`free`/`script` 두 가지 타입을 가진다.

```
{
  "id": "airport-checkin-en",
  "language": "en",
  "type": "free" | "script",
  "title": "공항 체크인",

  // type == "free"인 경우
  "persona_prompt": "너는 항공사 체크인 카운터 직원이다. ...",
  "goal": "체크인하고 좌석을 배정받는다",
  "max_turns": 8,

  // type == "script"인 경우
  "lines": [
    { "speaker": "bot", "text": "Good morning! Checking in today?" },
    { "speaker": "user", "text": "Yes, I have a reservation under..." }
  ]
}
```

- `free`: LLM이 페르소나로 자유롭게 응답하는 개방형 상황극. 세션이 너무 길어지지
  않도록 `max_turns`로 소프트 제한 (도달하면 자연스럽게 마무리하도록 유도).
- `script`: 실생활에서 자주 쓰이는 대화를 배우 대본처럼 미리 써둔 고정 스크립트.
  6~10줄 내외로 짧게 구성. 화면에 스크립트 전체를 보여주고 현재 줄을
  하이라이트한다. 봇 차례는 TTS로 읽어주고, 사용자 차례는 사용자가 말한 뒤
  "다음" 버튼으로 진행한다 (엄격한 발화 일치 판정은 하지 않음 — 부담을 줄이기
  위해). 세션 종료 시 사용자가 실제로 말한 내용(STT 인식 결과)과 스크립트 원문을
  비교해 참고용 피드백을 준다.

시나리오 콘텐츠(특히 script 타입의 대사)는 초기에는 직접 작성한 소수의 예시로
시작하고, 필요하면 나중에 늘린다.

### 수업 모드 (동적, 정의 파일 없음)
`lesson` 세션은 scenarios.json을 쓰지 않는다. 시작 시 사용자가 오늘 배우고 싶은
주제/문법 포인트를 자유롭게 입력(음성 또는 텍스트)하거나 비워둘 수 있다. 백엔드는
아래 정보로 "선생님" system prompt를 그 자리에서 조립한다.

- 해당 언어의 현재 추정 수준 (아래 수준 추정 참고)
- 사용자가 지정한 주제 (있으면), 없으면 "학생 수준에 맞는 적절한 문법/주제를 네가
  골라서 가르쳐라"라고 LLM에 위임
- 음성 대화라는 점을 고려해 한 번에 너무 길게 설명하지 말고, 설명 → 예문 →
  학생에게 문장 만들어보게 하기 → 교정 을 짧게 주고받는 흐름으로 진행하라는 지시

자유 상황극과 마찬가지로 세션이 너무 길어지지 않도록 소프트한 턴 제한을 둔다.

### 수준 추정
고정 프로필 설정 화면 없이, 세션 리포트 생성 시마다 LLM이 해당 세션의 대화
품질/오류를 바탕으로 수준(`beginner`/`intermediate`/`advanced`)을 함께 추정해
`sessions.level`에 저장한다. 언어별 "현재 수준"은 그 언어로 진행된 가장 최근
세션의 `level` 값을 사용한다 (세션 기록이 없으면 `beginner`로 시작). 이 값이
다음 수업 모드 세션의 system prompt에 들어간다.

### 저장소 선택 — 왜 SQLite인가
데이터 규모가 하루 약 100행, 1년 3만 행 수준이고 사용자는 1명, 쓰기는 분당 몇 건에
불과하다. 이 워크로드에서 서버형 DB는 이득 없이 비용만 늘린다.

- **실행 마찰이 가장 중요한 기준이다.** 이미 Ollama와 VOICEVOX 두 프로세스를 띄워야
  한다. 여기에 DB 서버(또는 Docker + Elasticsearch)를 더하면 "잠깐 연습하기"가
  서비스 여러 개 부팅부터 시작하는 일이 된다. 개인용 도구는 이런 마찰로 안 쓰게 된다.
- **PostgreSQL이 이기는 지점**(동시 쓰기, 네트워크 접근, 복제)이 전부 해당 없다.
- **Elasticsearch는 규모가 맞지 않는다.** 수백만~수십억 문서용 도구이고, 여기서
  얻을 실익은 과거 대화 전문 검색뿐인데 그건 SQLite **FTS5**로 충분하다. 한국어·
  일본어 검색을 제대로 하려면 nori/kuromoji 플러그인까지 필요해 설정만 늘어난다.
- 백업이 파일 복사 한 번이고, Python 내장 `sqlite3`라 의존성이 없다.
- 나중에 필요한 기능도 이미 있다: 전문 검색(FTS5), JSON 컬럼(JSON1), 누적 리포트와
  파인튜닝용 데이터 추출에 쓸 집계 쿼리.

재검토 조건: 세션이 수백 개 쌓인 뒤 의미 기반 검색이 필요해질 때. 그 경우에도 ES보다
`sqlite-vec` 확장이나 작은 로컬 벡터 인덱스가 가볍다.

**구현 방침**
- ORM을 쓰지 않는다. 테이블 3개에 SQLAlchemy는 과하다. 내장 `sqlite3` 위에 얇은
  데이터 계층 모듈 하나를 두고, 나머지 코드는 그 모듈만 거치게 한다. 저장소를
  교체할 일이 생기면 그 파일만 바꾸면 된다.
- **WAL 모드를 켠다.** FastAPI에서 SQLite를 쓸 때 `database is locked`가 나올 수
  있다. 단일 사용자라 실제로 겪을 가능성은 낮지만, WAL 활성화와 일관된 커넥션
  처리로 애초에 차단한다.

### DB 스키마 (SQLite)
- `sessions`: id, scenario_id(nullable, lesson 모드는 null), language,
  mode(free/script/lesson), topic(nullable, lesson 모드에서 사용자가 지정한 주제),
  started_at, ended_at, report, level(세션 종료 후 리포트와 함께 추정되는 값)
- `messages`: id, session_id, turn, speaker(user/bot), text, correction, suggestion,
  audio_path(nullable, 사용자 발화 녹음 파일), pronunciation(nullable, Phase 2에서 채움)
- `settings`: key, value — 언어별 선택 음성 등 사용자 설정을 보관하는 단순 KV 테이블

`correction`(문법 교정, 최대 2문장)과 `suggestion`(더 자연스러운 표현 추천, 최대
2문장)은 사용자 발화가 있을 때마다 채워진다. 세 모드 모두 동일한 방식으로
채워져 로그/리포트 파이프라인이 일관되게 유지된다 (lesson 모드에서 선생님이
대화 중에도 교정을 해주지만, 사이드 패널/로그용 2문장 요약은 별도로 남긴다).
대화 스크립트와 함께 영구 저장되어 나중에 다시 볼 수 있다.

## 핵심 기능

1. **자유 상황극 모드**: 시나리오 persona_prompt를 system prompt로 사용해 Ollama와
   대화. `max_turns` 근처에서 봇이 자연스럽게 상황을 마무리하도록 프롬프트에 지시.
2. **스크립트 롤플레이 모드**: 스크립트 라인을 순서대로 진행. 봇 라인은 TTS,
   사용자 라인은 사용자가 소리 내어 읽고 넘어감.
3. **수업 모드**: 봇이 선생님 역할로 문법/표현을 가르친다. 시작 시 주제를 자유롭게
   지정하거나 봇에게 맡길 수 있고, 최근 세션에서 추정된 수준에 맞춰 진행된다.
   설명 → 예문 → 직접 문장 만들기 → 교정의 짧은 사이클로 주고받는다.
4. **교정 + 추천 표현**: 사용자 발화마다 (a) 문법 교정 (b) 더 나은 표현 추천을
   각각 최대 2문장으로 생성해 화면 사이드 패널에 표시하고 DB에 저장. 세 모드 공통.
5. **세션 리포트**: 세션 종료 시, 전체 대화 스크립트 + 교정/추천 기록을 LLM에
   넣어 리포트를 생성한다 (자주 틀린 문법 패턴, 기억하면 좋은 표현, 짧은 총평).
   함께 수준(beginner/intermediate/advanced)도 추정해 저장한다. 리포트는 세션에
   귀속되어 DB에 저장, 나중에 다시 열람 가능.
6. **언어 토글**: 영어/일본어 전환, 시나리오 목록도 언어별 필터링.
7. **음성 선택**: 설정 화면에서 언어별 봇 음성을 고른다. 미리듣기 버튼으로 즉시
   확인할 수 있고, 선택은 영구 저장된다.

## 발음 정확도 평가 (Phase 2)
Phase 1 완성 후 추가한다. **스크립트 롤플레이 모드에만 먼저 적용** — 목표 문장이
확정되어 있어 비교 기준이 명확하고, 그만큼 피드백 정확도가 가장 높다. 잘 작동하면
다른 모드로 확장을 검토한다.

방식 (전부 로컬·오픈소스, 비용 $0):

```
녹음 오디오 → wav2vec2 음소 인식 모델 → 실제 발음한 음소열(IPA)
                                            ↓ 정렬·비교
목표 문장   → g2p(grapheme-to-phoneme)  → 발음해야 할 음소열(IPA)
                                            ↓
                        음소/단어별 정확도 + 자주 틀리는 음소 지적
```

- 음소 인식: `wav2vec2` 계열 phoneme 모델 (수백 MB, 4060 Ti에서 충분히 빠름)
- g2p: 영어 `g2p_en`, 일본어 `pyopenjtalk`
- 결과는 `messages.pronunciation`에 저장하고 세션 리포트에도 반영

한계 (설계 단계에서 인정하고 감안):
- 상용 발음 평가 서비스만큼 정밀하지 않다. "이 음소가 어색했다" 수준의 방향성
  피드백으로 다루고, 점수를 절대적 지표로 표시하지 않는다.
- 일본어는 영어보다 정확도가 낮다 (음소 모델 학습 데이터가 영어 편중).
- 목표 문장을 모르는 자유 대화에서는 STT 결과를 기준으로 삼아야 해서 신뢰도가
  떨어진다. 그래서 스크립트 모드부터 시작한다.

## 데이터 흐름 (자유 상황극 / 수업 모드 공통)
마이크 → 브라우저 STT → 텍스트 (수정 가능) → `POST /chat`
→ FastAPI: 세션의 대화 히스토리 + system prompt(모드에 따라 persona_prompt 또는
  선생님 프롬프트)로 Ollama 호출 (봇 응답 생성) + 사용자 발화에 대한 교정/추천
  생성 (별도 호출 또는 구조화된 응답)
→ bot_reply를 정제해 로컬 TTS로 오디오 생성 (캐시 히트 시 즉시)
→ 응답: { bot_reply, audio_url, correction, suggestion }
→ 프론트: 오디오 재생 + bot_reply 화면 표시, correction/suggestion은 사이드 패널에 표시
→ 메시지 DB 저장

세션 종료(`POST /sessions/{id}/end`) → 누적 메시지로 리포트 + 수준 추정 생성
→ DB 저장 → 화면 표시

## 구현 단계

**Phase 0 — 완료**
TTS 엔진 후보를 실제로 설치해 같은 문장으로 샘플을 생성하고 청취 비교했다.
영어 Kokoro / 일본어 VOICEVOX로 확정하고, 각 언어의 음성 후보와 기본값까지
청취로 결정했다. VOICEVOX는 Docker 기동까지 검증했다. 검증에 쓴 스크립트는
`docs/tts-spike/`에 남겼고, Kokoro 모델은 `engines/kokoro/`에 둔다(git 제외).

**Phase 1 — 쓸 수 있는 앱 만들기**
3개 모드(자유 상황극 / 스크립트 롤플레이 / 수업), 로컬 신경망 TTS 봇 음성,
음성 선택 설정, 교정+추천 표현, 세션 리포트, 수준 자동 추정, 대화 로그 저장.
사용자 발화 오디오는 녹음·저장만 하고 분석하지 않는다.

**Phase 2 — 발음 정확도**
스크립트 롤플레이 모드에 음소 단위 발음 평가 추가. Phase 1에서 쌓인 오디오에
소급 적용 가능.

## 에러 처리
- Web Speech API 미지원 브라우저 → 안내 메시지, 텍스트 입력만으로도 전체 기능 사용 가능하게 설계
- 마이크 권한 거부 → 녹음 없이 텍스트 입력으로 계속 진행 가능 (발음 평가만 비활성)
- Ollama 서버 미실행/응답 없음 → 명확한 에러 메시지 ("Ollama가 실행 중인지 확인하세요")
- TTS 생성 실패 → 브라우저 `speechSynthesis`로 자동 폴백, 품질 저하를 화면에 알림
- STT 인식 실패/낮은 신뢰도 → 사용자가 텍스트 입력창에서 직접 수정 가능

## 테스트 전략
개인용 도구이므로 광범위한 자동화 테스트는 하지 않는다.
- 유닛 테스트: 시나리오 로딩, 프롬프트 조립 로직, Ollama 클라이언트 래퍼,
  TTS 텍스트 정제 로직, 오디오 캐시 키 생성, (Phase 2) 음소열 정렬·비교 로직
- 나머지는 실제로 사용하며 수동 확인
- TTS/LLM 음성·문장 품질은 자동 테스트 대상이 아니다. 구현 초기에 영어·일본어
  샘플을 직접 들어보고 판단한다.

## 비용
$0 — Ollama(로컬) + 로컬 신경망 TTS + Web Speech API STT(브라우저 내장) +
SQLite(로컬 파일) + (Phase 2) wav2vec2·g2p 오픈소스 모델(로컬).
전기세 외 비용 없음.
